# Issue #53: browser takeover, heartbeat, and offline-conflict UX

> **For agent:** REQUIRED SUB-SKILL: Use subagent-driven-development (fresh subagent per task, two-stage review) to implement this plan.

## Goal

Make the React host acquire and renew the active-game claim, present an accessible Cancel/Take over decision for a live conflict, freeze displaced writers, and preserve offline work until takeover is explicitly authorized.

## Plain-language summary

A moderator opening a game controlled by another browser will see who claimed it and when. Cancel leaves the current browser read-only; Take over loads or retries the intended game under a new generation, while the old browser is stopped on its next heartbeat or save.

## Dependencies

Implement after both the [single-active-session invariant](./2026-09-03_174007-issue-53-active-session-invariant.md) and [server claim fencing](./2026-09-03_174007-issue-53-claim-fencing.md).

## Scope

### 1. Add RED client and claim-state tests

- Extend `apps/web/src/api/client.test.ts` to require claim headers on snapshot, semantic operation, and delete requests, plus typed acquire/renew/takeover/release responses and safe parsing of `game_session_claim_conflict` metadata.
- Add `apps/web/src/session-claim.test.ts` before production code for a small claim controller/persistence helper that proves:
  - a stable per-club/game UUID survives reload;
  - generation `0` is used only until first create acknowledges generation `1`;
  - 15-second renewal scheduling uses server responses and never relies on the browser clock as ownership authority;
  - transient network failure retains the credential and does not claim takeover;
  - a `409` transitions to displaced/conflict state and stops automatic save/heartbeat attempts;
  - explicit takeover replaces the generation and is the only path that re-enables blocked queued work;
  - completion, deletion, explicit release, and successful sign-out remove local claim state.
- Use fake timers and deterministic deferred promises; watch each semantic assertion fail for the missing behavior before implementation.

### 2. Add the browser claim transport and local controller

- In `apps/web/src/api/client.ts`:
  - define `GameSessionClaim`, safe conflict metadata, and claim response types;
  - add claim/acquire, takeover, and release calls;
  - accept a claim credential in `saveGameSession`, `saveGameSessionOperation`, and `clearGameSession`, sending exact `x-game-claim-id`/`x-game-claim-generation` headers;
  - retain structured error details on `ApiError` only for explicitly parsed safe fields.
- Add `apps/web/src/session-claim.ts` as the single owner of the per-club/game local claim key, status, generation, renewal timer, and subscription callbacks. Keep game state and outbox payloads in the existing `GameSessionOutbox`; do not duplicate them in the claim store.
- Have the outbox save/clear closures in `apps/web/src/App.tsx` read the controller's current credential at request time. Updating that credential is allowed only after first-create acknowledgement, expired/unclaimed acquisition, or explicit takeover.

### 3. Gate first save and restore behind ownership

- Update the club workspace in `apps/web/src/App.tsx` around the existing outbox setup (`GameSessionOutbox`), active-session loader, and `resumeSession` path so:
  - entering role giveaway creates a local claim ID and sends generation `0` with the first durable snapshot;
  - a first-save `club_active_game_exists` response stops creation, preserves local work, refreshes the sole active summary, and opens the conflict decision instead of presenting a generic connection error;
  - a local persisted session renews/acquires its claim before automatic outbox flush; legacy local envelopes without claim state do not write until that step succeeds;
  - resuming the remote active game claims first and applies the remote session only after ownership succeeds;
  - latest-request-wins guards remain in place so a delayed claim/session response cannot overwrite newer local setup or a newer takeover.
- Keep `listActiveGameSessions` array-compatible but update tests and rendering assumptions to zero-or-one active row.

### 4. Render an accessible takeover decision and freeze stale clients

- Add an in-app `role="alertdialog"` in `apps/web/src/App.tsx` with focus-safe **Cancel** and **Take over** buttons, holder display name, localized claim time, and expiry/recovery explanation.
- Add English, Spanish, and Russian messages in `apps/web/src/i18n/messages/shell.ts`; format times through the existing i18n formatter rather than exposing raw timestamps.
- Add narrowly scoped styling in `apps/web/src/styles/app.css`, reusing the current glass/drawer visual language.
- While claim state is conflicted/displaced:
  - gate all game/setup mutation handlers, keyboard paths, outbox retry controls, resume/delete actions, and delayed component callbacks;
  - leave the existing local snapshot and pending outbox intact;
  - show ownership conflict as distinct from offline/unreachable and ordinary validation rejection.
- **Cancel** closes the prompt but leaves the workspace visibly read-only/blocked. **Take over** calls the takeover endpoint; for a remote resume it then fetches/applies that remote session, and for this browser's retained local queue it deliberately updates the fence and invokes retry.

### 5. Renew and release across lifecycle boundaries

- Renew every 15 seconds while this browser owns an active local session; renew immediately after visibility/reconnect recovery before allowing a flush.
- Treat transport failure as offline-first: preserve edits/outbox and retry connectivity without silently changing generation. Treat claim conflict as terminal until the user chooses takeover or discards/exits.
- On server-confirmed completion, session deletion, and explicit local clear, stop timers and remove the local claim record.
- On club exit or sign-out, attempt exact release before clearing local claim state. Release failure must not trap the user in the account; report it and rely on the 45-second server expiry.
- Ensure component teardown cancels timers/listeners and cannot publish stale heartbeat success after club/session replacement.

### 6. Add deterministic two-client UI coverage

- Extend `apps/web/src/App.test.tsx` with deferred API mocks representing clients A and B:
  - A owns the session; B's resume receives conflict metadata and renders the exact safe holder/time plus Cancel/Take over controls;
  - Cancel performs no mutation and leaves B blocked;
  - Take over advances B's generation, applies the intended remote session, and ignores late pre-takeover responses;
  - A's next heartbeat/save receives the stale-generation conflict, keeps its local outbox, disables mutation controls, and does not auto-replay;
  - B continues saving, and A can write again only after A explicitly takes over in turn;
  - an expired claim acquires without prompting;
  - completion/delete/sign-out stop heartbeats and release/clear claim state.
- Replace the existing “two active sessions” latest-request fixture with zero-or-one active-session scenarios while retaining latest-request-wins coverage for delayed resume versus newer local setup.
- Add a focused browser smoke check with two isolated browser storage contexts against the local app: claim in A, conflict/cancel in B, takeover in B, then verify A is blocked and B saves. Record observed behavior; do not add a new permanent E2E framework solely for this issue.

## Non-goals

- WebSocket notifications or real-time collaborative indicators.
- Automatic last-write-wins merging between browsers.
- Discarding or uploading a displaced browser's outbox without an explicit user decision.
- Redesigning the active-game management drawer beyond the ownership controls needed here.
- Changing game rules, replay hashes, or terminal result semantics.

## Done when

- The second browser cannot write without a visible explicit takeover.
- The old browser is deterministically fenced and keeps unsynced work local.
- Expired claims recover automatically, lifecycle releases are safe, and the user can distinguish ownership conflict from network outage.
- The UI, localStorage, API, and database agree on the same game ID and claim generation throughout the tested races.
