# Completed-game saving repair plan

## Plain-language summary
Use the improved error details and a reproducible failure to correct the save path so valid completed games reach the server reliably. Show permanent rejections as blocked saves rather than telling the user merely to reconnect. Existing-game recovery is excluded.

## Goal
Persist valid completed games exactly once while preserving truthful failure reporting and server integrity protections.

## Prerequisite / readiness
Diagnostics first. The exact original failure has not been captured, so a root-cause code patch is not yet implementation-ready. Initial approved work is evidence collection and reproduction; finalize the patch design against those results. Do not assume the tombstone caused yesterday's first failure or that the independently reproduced voting mismatch was the user's action.

## Investigation and implementation
1. Recheck the current source, local service identities, and the iPad's current origin. Use an existing browser/network inspection route or have the user retry using the save toolbar and share the richer console entry. Do not read credentials or dump request headers. Keep any necessary private game fixture under .AI/ and uncommitted; prefer an anonymized deterministic fixture after preserving canonical relationships.
2. Distinguish current missing/deleted-game rejection from the historical save failure. Trace the actual endpoint response through client.ts, App.tsx, session-claim.ts, session-retry.ts, and session-outbox.ts to server validation and GameSessionStore. Use existing tests rather than inventing a new recovery subsystem.
3. Reproduce the reported failure in isolated tests. If only the final-candidate vote mismatch can be reproduced, state that honestly and verify its end-to-end consequence before proposing its fix. Check neighboring provisional-state callers for the same mismatch.
4. Record the proven invariant disagreement and minimal repair in this plan before changing behavior. Preserve canonical replay, strict club identity, claim fencing, tombstones, exact mutation retries, and one-active-game rules. No replacing server validation with permissive acceptance. Material game-rule changes require a scope checkpoint.
5. Add focused red/green coverage through the real relevant client/server seam. Exercise a valid game reaching completion, failed upload, subsequent retry, reload restoration, server completed status/results, canonical history, and unchanged statistics on an exact retry.
6. Ensure rejected/deleted/missing saves are not presented solely as connectivity failures. Pass the existing terminal reason through the completion UI as needed, keeping the saved/offline distinction explicit and the save toolbar available where retry is meaningful. Update English and Russian messages and tests together. Do not add deletion/recovery controls.
7. Verify the reproduced failure is fixed, then run the complete local gate with npm run check:local (scripts/test-local.mjs invokes npm run check against owned disposable mafia_test). Never test against mafia_local or production.

## Non-goals
No recovery of the deleted game, tombstone removal, local-data discard, production data manipulation, reset, new import/export feature, schema migration, dependency update, broad UI redesign, or unrelated voting behavior changes.

## Acceptance / verification
- A failing regression reproduces a demonstrated save defect before the patch and passes after it; historical incident attribution is qualified if not proven.
- A valid completed game persists with final results and replay integrity; failed saves survive reload, a successful retry clears pending state, and an exact retry adds no duplicate statistics.
- Permanent rejections remain protected and are clearly distinguished from unreachable-server failures.
- Existing isolation, secrecy, claim, deletion, and idempotency tests remain passing; relevant browser/component coverage and npm run check:local pass.
- Record actual test commands/results. No incident-resolution claim based solely on green mocked tests.

## Risks
The original server row is deleted, and access to the iPad may require user participation. Fresh code now includes separate orphan recovery changes; preserve them. Client edits can hot-reload the active iPad; coordinate rather than clear its storage. If the reproducer points beyond the scoped save behavior, stop and refine instead of accumulating speculative fixes.
