# Subtle interior flame implementation plan

Status: implemented; real-GPU containment/motion, responsive composition/readability, fallback and full local check passed. Michael's visual acceptance on Mac/iPad remains pending. Evidence and actual-animation recording: ../card-fire/implementation-report.md.

**Goal:** Replace both current GPU fire uses with natural-looking flames contained inside each card while keeping all card information readable.

**Plain-language summary:** Replace the repetitive flames above the cards with quiet, irregular flame ribbons behind the contents, clipped to the card's rounded interior.

**Architecture:** Retain the existing shared V-GPU renderer and semantic fire flag. Rework fire geometry/noise and compositing separately from ordinary LED spill and table ambience; avoid a new rendering framework or an extra canvas per flame unless a demonstrated constraint requires reconsideration.

**Tech stack:** React, V-GPU/WGSL, CSS, existing browser/GPU probes and Vitest.

**Non-goals:** Exact copying of ThreeUI code or its logo/embers, package installation, actual ray tracing, changes to non-fire lighting or table ambience, new fire settings, SVG fallback, backend/data/deployment work.

- apps/web/src/features/effects/vgpu/lighting-shader.ts:108-118 composites fire and ordinary player glow.
- apps/web/src/features/effects/vgpu/VgpuLightingCanvas.tsx:60-71 sets fire for kind mafia.

- Current CSS legacy flames at app.css:1436-1462 also extend outside the card; fallback must meet containment/readability without attempting to fake GPU realism.
- Reference https://threeui.com/backgrounds/elements/elemental-flame describes noise-driven ribbons and exposes opacity/brightness controls. Main live preview was black in inspected browser; do not claim visual reproduction from its description alone.

## Steps
1. Inspect the existing runtime/tests and .AI/lighting-polish GPU/fixture probes before reuse. Recover a working reference animation through its public preview if possible; treat it as inspiration, not automatically licensed source to copy.
2. After approval, build a small isolated animated card preview before full integration. Use warm irregular upward flow, layered turbulence, soft thinning tips, and restrained luminosity. Start energy near the interior bottom/sides and fade toward the central information. Avoid repeated evenly spaced flame spikes and flashes. Show selected availability and Mafia card examples at actual card sizes for user visual feedback.
3. Add failing real-GPU pixel checks: the fire contribution is nonzero inside and zero outside the rounded card, temporal variation with pulse disabled, and frozen fire under reduced motion. Compare fire-on versus fire-off with identical glow/time/config so preserved exterior LED light does not invalidate containment assertions. Replace obsolete outside-flame/transparent-center expectations rather than retaining contradictory tests.
4. Rework player_fire with continuous domain-warped noise and a rounded-interior mask. Bound opacity/luminance; keep brighter turbulence away from names/status. Preserve pulse settings and non-fire/table shader behavior. Do not add costly multi-pass/raymarch rendering by default.
5. Correct card-local layering so fire sits above the opaque background but below icons, names, badges and game controls. Preserve existing exterior ordinary glow through a separate shader mask/compositing path, not overflow:hidden on the entire card. Avoid negative-grid stacking for interior fire. Keep canvases pointer-events:none and ensure neighbors never receive fire pixels.
6. Replace the old outward CSS flame fallback with a quiet interior/static warm treatment for these same semantic states; keep binary selection recognizable when GPU is delayed, unavailable, disabled or fails. No SVG and no fake assertion of GPU equivalence.
7. Run focused shader/runtime/canvas/component tests and real browser checks. Capture dense selected grids and Mafia highlights on desktop, phone and tablet/DPR2, including scrolling, long names, card controls, reduced motion, pulse-off, GPU loss and lighting-disabled behavior. Measure text contrast over representative animation frames (normal text at least 4.5:1) and verify frame pacing against the existing renderer baseline. Inspect actual rendered animation, not mock-adapter compile results alone.
8. Rebuild/refresh the running frontend without altering persistent local data. Present the real animation on the existing Tailscale origin for Mac/iPad acceptance; do not equate an emulated tablet or unsafe-GPU-flag browser with the physical device. Run npm run check:local before final delivery.

## Acceptance
Both confirmed fire uses have visible but subtle, irregular interior motion, no external fire, readable stationary foreground information, and usable controls. Non-fire light spill/table ambience/settings remain unchanged. Motion freezes for reduced motion. User approves the actual appearance on Mac/iPad; test passes alone cannot establish that the flame is sufficiently lifelike.

## Risks and stop conditions
Layering changes can hide the fire or clip wanted ordinary light; shader bounds and browser screenshots must check both. Mobile GPU cost and changing text contrast can undermine usability. If the requested visual quality requires a new dependency/renderer, copying third-party source, or material scope expansion, return for approval rather than silently changing architecture. Keep development data and unrelated uncommitted work intact.
