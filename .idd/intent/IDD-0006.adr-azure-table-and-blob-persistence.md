# IDD-0006.adr-azure-table-and-blob-persistence

## Status

Accepted

## Context

This application serves a few clubs and occasional simultaneous moderated games. Its structured dataset is small, while a dedicated always-on PostgreSQL service has a disproportionate recurring cost. Acknowledged saves must survive application restarts; brief downtime is acceptable.

IDD-0001 owns club authorization, consent and permanent player identities. IDD-0004 owns browser-authoritative snapshots, atomic projection synchronization, recovery and deletion. IDD-0005 owns supported-format admission and preservation. Changing the persistence implementation must not change these contracts.

## Decision

Use Azure Table Storage for typed application records and synchronized query projections, with private Azure Blob Storage for complete immutable game revision envelopes and oversized values such as club logos. Do not fully normalize canonical event payloads or game snapshots into independently editable records. Ordinary persistence preserves accepted snapshot identity strings and retained replay hashes exactly. A completed envelope may carry partial factual results without playable history; an active envelope must retain truthful resume/correction state.

Use one authoritative application partition for this small deployment. Every structured mutation includes a conditional update of its versioned control record in the same entity-group transaction. Create the private blob before atomically publishing its reference and related projections. Confirm remote publication before acknowledging success. Stable reads check the control version before and after assembling rows and selected blobs; a missing or corrupt authoritative object is an error, not permission to fall back or reset.

Keep creation mappings and deletion markers so stale saves and original creation retries cannot recreate deleted games. Retirement must inspect active authoritative snapshots, including partial setup, and revalidate against competing writes. Club deletion makes the club unavailable before the existing bounded, manually resumable purge attempts. Its successful result acknowledges application deletion, not complete physical erasure: an outstanding Blob upload can finish afterward, and neither immediate nor eventual removal of every private file is guaranteed. No background cleanup/retry service or upload lock is required for this whole-club deletion contract.

Application-local files are not the production durability authority. Production storage access uses server-side identity and authorization; no game blobs become public and no storage credentials are provided to the browser. Explicit initialization may create an empty recognized dataset; existing unrecognized or incompatible data is preserved and rejected.

Azure Table and private Blob Storage are the only supported application backend. There is no PostgreSQL runtime/reference backend, SQL-to-Azure importer, PostgreSQL-based Compose deployment, automatic fallback or dual writing. Existing Azure development, deployment and backup/recovery remain supported. Retiring PostgreSQL software support does not authorize deleting existing databases, data directories, archives or cloud resources; the application does not convert or erase those originals.

Requests from older browsers remain subject to ordinary authentication, authorization and supported-data validation; no additional dataset-epoch rejection, outbox quarantine or mandatory browser cleanup is required. Existing deletion and idempotency protections remain in force. Stored recovery metadata does not imply browser enforcement.

Business records do not identify a rules engine. Storage/data-shape versions, dataset identity, revisions, checksums and recovery metadata remain operational, never gameplay selectors. IDD-0005 permits only an explicit one-time historical normalization outside ordinary runtime: preserve every game and known fact/relationship, keep faithful optional timelines, and stop rather than lose active or unsent state. Verified representation conversion may replace immutable envelopes and corresponding hashes through the same atomic publication/projection protocol; normal reads, saves and recovery never do so. Any predecessor decoder stays in private local operational material, not a shipped compatibility layer.

Production normalization requires separately authorized target-bound writes, exact inventory/dry-run dispositions, proven private backup/recovery and an explicitly authorized compatible app/data maintenance sequence. Local rehearsal and read access are not production mutation or deployment authority. Originals remain recoverable; an image-only rollback is not proof that changed data can be read or that subsequent writes can be preserved.

## Alternatives Considered

- **Smaller or sleep-when-idle managed PostgreSQL:** lower migration effort and relational constraints, but not the owner's selected Azure Storage direction.
- **Local SQLite with periodic Blob uploads:** simple local access, but acknowledging changes before remote publication can lose saved games on container replacement. Shared filesystem SQLite also introduces locking and deployment restrictions.
- **Blob-only application state:** inexpensive but requires manually coordinating permissions, uniqueness, listings and synchronized query projections.
- **Full game normalization before switching stores:** unnecessary intermediate SQL work; the exact snapshot remains the recovery authority and the existing database already maintains selected projections.
- **Sharding or a distributed transaction coordinator:** unjustified for the confirmed few-club workload and substantially more complex.

## Consequences

- Storage costs should track retained bytes and operations rather than an always-on database server; actual billing remains deployment-specific.
- A shared control row deliberately trades throughput for simple atomicity. Contention is bounded and retryable, not a client revision fence or exclusive host claim. Growing workload may require a separately designed partitioning strategy.
- Azure Tables' operation, request, entity and property limits must be enforced. Large variable payloads belong in blobs. An exceptional oversized account-linking operation fails without partial acceptance; no new batching or invitation workflow is introduced for the confirmed workload.
- Game histories do not create an unbounded number of Table operations per save. Query metadata and projections remain bounded; history and statistics may scan paginated club-local ranges rather than claim SQL-style secondary indexes.
- Existing owned cleanup and manual recovery for failed or superseded immutable objects remain. Whole-club deletion does not guarantee that this machinery will eventually erase every leftover file; private bytes may remain indefinitely without later intervention. Live objects, consent/individual-retirement cleanup, independent archives and backup retention remain separate concerns.
- Table redundancy and Blob versioning are not a consistent application backup. A backup must include typed entities and all referenced blob bytes, and be independently restorable. Backup execution is a separate implementation boundary.
- Azurite verifies local behavior but cannot prove production RBAC, networking, service limits or live disaster recovery. Those remain explicit production qualification gates.
- Application startup and maintained local verification do not require a PostgreSQL service or client tools. Retiring SQL-specific qualification does not remove the authorization, supported-format, canonical-preservation, idempotency or recovery guarantees of the Azure application.
