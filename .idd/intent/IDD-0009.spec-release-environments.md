# IDD-0009.spec-release-environments

## Intent

New Mafia Dashboard releases are tested in an automatically deployed staging
environment before Michael explicitly releases them to production. Staging
activity must not read, modify, or replace production application data.

## Related Specifications

- IDD-0001 owns account, club, membership and player authorization.
- IDD-0004 owns durable game records and continuity.
- IDD-0005 owns data compatibility and preservation.
- IDD-0006 owns Azure Table and private Blob persistence.
- IDD-0008 owns the independent public website and its publication.

## Behavior

- Changes pushed to the trusted main branch are automatically verified, built
  and deployed to staging. Unpublished local edits do not trigger deployment.
- Staging has its own origin, accounts, clubs, sessions, games, uploaded assets
  and provider authorizations. It begins empty; production data is not copied
  into staging as part of provisioning or release.
- Staging data persists across ordinary application deployments. Deploying an
  application does not reset, reseed, synchronize or initialize existing data.
- Production deployment requires an explicit manual GitHub action. A push,
  successful build or successful staging deployment never deploys production.
- Manual production release selects a successfully verified staging release.
  The normal selection is the currently verified staging release; an operator
  may explicitly select another successful staging release. Selection freezes
  the release identity before deployment, so concurrent staging changes cannot
  silently substitute a different release.
- Production receives the exact immutable application image tested on staging,
  retaining its original commit and displayed version, rather than a rebuild.
  Its own configuration, origin and data remain in use. Promotion copies code,
  not accounts, games, sessions, media, provider tokens or storage contents.
- Missing, failed, incomplete, mismatched or no-longer-available release
  evidence blocks promotion. A mutable tag is not evidence of a verified
  staging release.

## Product-Significant Architecture And Constraints

- Staging and production use separate application instances, dedicated storage
  accounts and runtime identities. Each runtime identity can access only its
  own environment's application data. A different partition in a shared
  account is not sufficient isolation.
- Deployment identities and protected environment configuration are separate
  and scoped to their matching environment. Staging deployment must not obtain
  production credentials or authority to change production resources.
- Encryption keys and provider authorization storage are not shared between
  environments. The source repository, immutable image registry and cloud
  subscription may be shared; this is not isolation from authorized cloud or
  repository administrators.
- First-time empty-storage initialization is explicit and cannot become an
  ordinary deployment default. Compatibility and preservation rules remain
  applicable to both environments.
- Deployment success requires the serving release to match its selected image,
  commit and version and to pass application readiness checks. Deployment
  acceptance is distinct from full user-interaction or OAuth acceptance.
- Staging setup and routine releases preserve production's current serving
  release until an explicit production deployment is requested.

## Non-Goals

- Automatically publishing the separate public club website.
- Copying, synchronizing or anonymizing production data for testing.
- Automatically promoting releases, or deploying untrusted pull requests with
  protected credentials.
- Treating an application rollback as a data rollback or an independent backup.

## Acceptance Criteria

- A trusted main-branch push produces a verified staging release without a
  production deployment.
- A staging-only test record survives an ordinary deployment and is not present
  in production by virtue of that deployment or promotion.
- Staging's runtime and deployment identities have no production data/resource
  grants; wrong-environment bindings fail closed.
- A manual production action identifies and deploys a verified staging image
  without rebuilding it or changing the production data namespace.
- Failed or missing release evidence refuses promotion; concurrent staging
  updates do not change an already selected production release.
- Release status identifies the source commit, displayed version and immutable
  image, and does not confuse a submitted deployment with verified success.

## Verification

Automated coverage exercises trusted trigger selection, manual-only production
release, wrong-environment rejection, immutable successful-release selection,
version preservation and refusal of incomplete or mismatched evidence. Live
qualification establishes separate target resources and identity scopes,
staging-only persistence across release, denied production access from staging,
and unchanged production bindings during staging deployment. The first real
production promotion remains an explicitly authorized operator action rather
than an implicit setup test.
