# IDD-0009.spec-release-environments

## Intent

Mafia Dashboard changes are checked before release. Routine updates to the
existing production application require an explicit manual release from trusted
`main`. An ordinary release changes application code, not the production
dataset.

## Related Specifications

- IDD-0001 owns account, club, membership and player authorization.
- IDD-0004 owns durable game records and continuity.
- IDD-0005 owns data compatibility and preservation.
- IDD-0006 owns Azure Table and private Blob persistence.
- IDD-0008 owns the independent public website and its publication.

## Behavior

- Pull requests and pushes to `main` run CI only. They do not publish container
  images or deploy the application. Unpublished local edits do not trigger CI or
  release.
- The manual production release checks the exact commit selected by the trusted
  `main` dispatch, then builds and publishes one application image for that run.
  Failed checks, a failed publication or missing or mismatched image evidence
  block deployment.
- Production receives the exact image digest verified in the registry for that
  run, with its original source commit and displayed version. Deployment does
  not rebuild the image, use a mutable tag as the release identity, or select an
  artifact from another release run.
- The existing production application, origin, runtime identity and durable
  data bindings stay in use. Release does not provision or reconcile the
  foundation, initialize storage, rotate secrets, or reset, migrate, copy or
  restore data.
- The public club website has its own publication action. Neither publication
  triggers or substitutes for the other.

## Product-Significant Architecture And Constraints

- Production deployment credentials are limited to the protected production
  release path. CI and untrusted refs cannot obtain production deployment
  authority. The application's runtime identity remains scoped to its own data.
- Missing or mismatched production targets and bindings fail closed. Empty-store
  initialization and infrastructure changes require separate explicit
  authorization; they are not part of routine release.
- Production releases do not overlap. A newer release cannot change the image
  selected by an in-flight deployment.
- Deployment success requires production to serve the expected immutable image,
  source commit and displayed version, with the expected configuration and
  application readiness. A submitted change is not verified success. These
  checks do not establish full interactive or OAuth acceptance.

## Non-Goals

- Automatic deployment, an intermediate deployment or promotion environment,
  and using production data as a test fixture.
- Publishing the separate public website as part of an application release.
- Treating application rollback as a data rollback or an independent backup.

## Acceptance Criteria

- A pull request or `main` push can pass CI without publishing an image,
  deploying to Azure or publishing to Pages. A manual dispatch from any other
  ref cannot release the app.
- One authorized `main` release runs the quality gate, builds and publishes one
  image, then deploys the verified digest from that run to existing production.
  A failed gate or an invalid digest or target prevents deployment.
- The production origin, configuration and data bindings are preserved. A
  release is only reported as verified when its actual configuration and serving
  identity match the expected image, commit and version and readiness passes.
- Rollback uses a known-good compatible immutable image without changing the
  production dataset. Existing backups are preserved and data recovery requires
  a separate decision.

## Verification

Automated coverage verifies CI-only triggers, manual trusted-main release,
one-build immutable handoff, wrong-target rejection, production binding
preservation, and failure on incomplete release evidence or mismatched readback.
A separately authorized live release must confirm the existing production
configuration, serving digest, commit, version and readiness. Local checks do not
establish live qualification; do not deploy production merely to verify the
workflow change.
