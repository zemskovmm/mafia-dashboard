# IDD-0005.spec-data-compatibility-and-preservation

## Intent

Make incompatible stored data fail safely without silent reset, conversion or loss, while maintaining a clear boundary around supported game records.

## Related Specifications

- IDD-0001 defines consent and identity erasure with retained shared history.
- IDD-0002 defines the retained saved-Casper behavior.
- IDD-0004 defines current game persistence, local recovery and deletion.

## Behavior

### Database compatibility

- Support an empty database or the current database schema.
- Reject the prior claim-controlled schema, unknown schemas and incomplete historical schemas before modifying them. Do not automatically upgrade the prior claim-controlled structure.
- Incompatibility must not trigger reset, broad backfill or deletion. Preserve the original data and report the unsupported state.

### Browser-local compatibility

- Invalid or unsupported current browser-session data blocks gameplay until explicit clearance of the exact inspected record.
- Do not silently repair, migrate, overwrite or recover through an undisclosed fallback.
- Clearance must not erase a newer or different local record or unrelated local work merely because an earlier inspected record was invalid.

### Supported game meaning

- Support the current identity-only game format and its canonical replay integrity contract. Reject older name-bearing game snapshots, baselines, events, host material and results on admission rather than converting, stripping, rehashing or silently clearing them.
- Newly initialized current-format games follow the corrected gameplay rules in IDD-0002. No separately published earlier identity-only rules format is promised; rejection of old name-bearing records does not change their recorded game meaning or turn them into playable current-format games.
- Preserve rejected originals without modification. Unsupported server records do not expose their identifying contents through supported game list, detail or event responses; browser-local invalid records block play until guarded clearance of the exact inspected record. Rejection is not an erasure of old stored names and does not authorize resetting a real database.
- Preserve the explicitly supported saved-Casper Best Move eligibility defined by IDD-0002. This exception does not imply support for arbitrary historical envelopes or data migrations.
- Application rollback does not prove database rollback or archive compatibility. Compatibility failure must preserve the original data rather than reset it to make an application start.

## Product-Significant Architecture And Constraints

Compatibility checks must precede changes to unsupported data. Safe rejection is a valid outcome; silent conversion or deletion is not. This contract does not select a permanent framework, database provider or hosting architecture.

## Non-Goals

- General historical upgrades, automatic repair or indefinite compatibility with every past stored format.
- Reintroducing host claims or upgrading their retired database structure.
- Establishing numerical recovery objectives, backup-retention promises, hosting topology commitments or architecture durability.

## Acceptance Criteria

1. Empty and current database states are supported; prior claim-controlled, unknown and incomplete schemas are rejected without mutation or reset.
2. Unsupported browser-session data prevents play until explicit guarded clearance.
3. A newer or replaced local record survives an attempted clearance based on stale inspection.
4. Newly initialized supported current game data round-trips with its corrected gameplay meaning, integrity guarantees and saved-Casper exception intact.
5. An incompatible rollback or recovery target remains preserved and is not automatically reset or backfilled.
6. Old name-bearing game payloads are refused without mutation or exposure as supported game content; supported identity-only records round-trip without copied profile fields and without server-side gameplay validation.

## Verification

Compare stored data and structure before and after rejected compatibility operations, not only error messages. Exercise empty/current databases, a recognized prior claim-controlled schema and unknown or incomplete shapes. Reject name-bearing browser/server payloads and prove original bytes remain intact without their exposure through supported record views. Verify exact-record clearance against concurrently replaced local data, newly initialized identity-only live/replay round-trips with corrected rules, and supported saved-Casper semantics. Keep compatibility proof separate from any claim about production backup, name erasure in rejected originals or recovery readiness.
